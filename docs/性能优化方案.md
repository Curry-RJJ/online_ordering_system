## 1. 目标与约束

### 1.1 优化目标

- 在**不牺牲安全与数据一致性**的前提下，降低首屏与列表页延迟、提高吞吐、减轻源站与数据库压力。
- 为后续用户量增长预留**可观测、可回滚**的调参空间。

### 1.2 当前环境与硬约束


| 项目    | 说明                                       |
| ----- | ---------------------------------------- |
| 服务器规格 | 腾讯云 **2 核 2G**（见部署清单），CPU 与内存为首要瓶颈       |
| 应用进程  | 生产环境经 **Gunicorn** 启动（见 `entrypoint.sh`） |
| 入口    | **Nginx** 反向代理、HTTPS、静态目录直出              |
| 数据    | **MySQL** 持久化；**Redis** 用于缓存与限流等         |


**原则：** 优先做**可度量、低成本、高收益**项；架构级改造（读写分离、分库）仅在监控证明必要时启动。

**〔§4.1 实施标注〕** **① Gunicorn 日志**：已落地——`docker-compose` 中 `web`/`celery_worker`/`celery_beat` 挂载 `./logs:/app/logs`，与 `entrypoint.sh` 中日志路径一致。**② MySQL 慢查询**：已落地——`mysql` 服务启用慢查询日志并挂载 `logs/mysql/`（见实施明细表 P0-2）；**按慢日志做 Top SQL 分析**为持续运维动作，不在仓库内自动完成。**③ 健康检查**：应用已提供 `/health`（见 `app/__init__.py`）；外部 crontab/告警见部署清单。

### 4.2 Gunicorn 与 2C2G 匹配

当前生产命令（摘录）：

```text
gunicorn --bind 0.0.0.0:5000 --workers 2 --threads 4 --timeout 120 ...
```

**说明：** 在 **2 核 2G** 环境下，`workers=4` 可能导致内存紧张与过多进程竞争。建议：

- 使用 **wrk / Locust** 等对首页、餐厅列表、下单路径做压测；
- 在内存占用与 P99 延迟可接受前提下，尝试 `**workers` 2 + `threads` 2～4** 等组合；
- 以**实测结果**为准更新 `entrypoint.sh`，并在本文档或变更说明中记录压测结论。

**〔§4.2 实施标注〕** **基线参数**：已改为 `workers=2`、`threads=4`（`entrypoint.sh`），与上文代码块一致。**压测验证**：尚未在文档中记录 wrk/Locust 结论——验收通过压测后，请更新本段说明并勾选 §11「workers/threads 经压测定型」。

### 4.3 数据库连接池

- 核对 **SQLAlchemy** 的 `pool_size`、`max_overflow`、`pool_recycle` 与 MySQL `max_connections`、Gunicorn 进程数的关系，避免出现**连接耗尽**或**闲置连接过多**。
- 修改配置后应做一次压力测试验证。

**〔§4.3 实施标注〕** **已落地**：生产环境在 `app/__init__.py` 中设置 `pool_pre_ping`、`pool_size`/`max_overflow` 默认值，并支持 `SQLALCHEMY_POOL_SIZE`、`SQLALCHEMY_MAX_OVERFLOW`、`SQLALCHEMY_POOL_RECYCLE`。**与 MySQL `max_connections` 的核对**需在具体部署上按进程数（Gunicorn + Celery）估算后留档；压测建议同 §4.2。

| 序号  | 任务           | 说明                                           |

| 1   | 按慢查询日志排序     | 优先处理**频率高**且**单次耗时高**的语句                     |
| 2   | 使用 `EXPLAIN` | 关注 `type`、`key`、`rows`，减少全表扫描                |
| 3   | 复合索引         | 对典型 `WHERE + ORDER BY` 组合建立合适复合索引（需结合具体 SQL） |


**〔§5.1 实施标注〕** **已落地（示例）**：迁移 `b2c4e6a8d0f1` 为 `order` 表增加 `(user_id, created_at)`、`(restaurant_id, created_at)` 复合索引，对应用户订单列表与商家订单列表常见排序。**持续优化**：仍应结合 `logs/mysql/slow.log` 中 Top SQL 迭代；每新增一批索引请在「实施记录（明细）」表与本文档同步一行。

### 5.2 ORM：避免 N+1

- 列表页、订单详情等若在循环中访问关联对象，改为 `**joinedload` / `selectinload`** 等预加载，或合并查询。
- 改动后可用日志或 SQL 计数对比请求内 SQL 条数。

**〔§5.2 实施标注〕** **已落地**：订单列表/详情/商家管理（`app/routes/order.py`）、API 订单详情（`app/api/orders.py`）使用 `selectinload`/`joinedload`；`Order.order_items` 改为 `lazy='select'`（`app/models.py`）；管理员菜品列表（`app/routes/dish.py` → `admin_dishes`）预加载餐厅与分类。

### 5.3 地理位置相关（若数据量持续增长）

- 当前有基于 Haversine 的距离筛选与排序；数据量增大时，可考虑**矩形边界预筛选**再精算距离，必要时引入**空间索引**（需评估 MySQL 版本与字段设计）。

**〔§5.3 实施标注〕** **已落地（应用层）**：`list_restaurants` 在 session 中有用户坐标且需计算距离时，对有坐标的餐厅先用 **轴对齐外包矩形**（半径 10 km 与现有过滤一致）排除不可能命中的点，再调用 `haversine`。**未落地**：MySQL 空间索引 / SQL 侧地理过滤——若全表餐厅数极大且慢查询指向本接口，再评估下推到数据库。

## 6. P1 — 边缘与静态资源

### 6.1 Nginx 静态缓存

- 已有 `/static/` 的短期缓存；若前端对 CSS/JS 使用**文件名带内容 hash**，可对这类资源配置**更长 `max-age`** 与 `immutable`，减少重复请求。
- **HTML 页面**宜保持较短缓存或依赖协商缓存，避免发版后用户长期看到旧页。

**〔§6.1 实施标注〕** **已落地**：`/static/` 仍为短缓存（`nginx/nginx.conf`）；已为带内容 hash 的构建产物增加 `**location /static/dist/`**（长缓存 + `immutable`），目录占位 `app/static/dist/`。**发版策略**：无 hash 的 CSS/JS 继续走短缓存；若未来引入 hash 产物，放入 `static/dist/` 并在此文档备注发版流程。

## 7. P2 — Redis 缓存扩展与传输优化

### 7.1 只读热点接口缓存

- 对**读多写少**的接口（如餐厅详情、菜单聚合）可参照 `restaurant.py` 中的模式：**短 TTL + 写操作失效**。
- 注意缓存**键命名空间**与**并发下的一致性**（必要时先删缓存再写库，或接受短暂不一致并在文档中说明）。

**〔§7.1 实施标注〕** **已落地（本轮）**：菜单聚合使用 `restaurant_menu_cache_key` / `restaurant_ajax_menu_cache_key`（版本号键含 `menu_ver:{餐厅id}` 与 `menu_ver_global`）；餐厅/分类侧写操作沿用 `_invalidate_restaurant_cache`；**菜品**增删改、上下架、强制删除后调用 `_invalidate_restaurant_cache`（`app/routes/dish.py`）。餐厅列表、API 列表等原有缓存逻辑不变。**说明**：评价列表仍为实时查询，与方案一致。

### 7.2 Redis 自身

- 配置 `**maxmemory`** 与 `**maxmemory-policy**`，避免缓存挤占导致 OOM，影响会话或限流依赖的 Redis 使用。

**〔§7.2 实施标注〕** **已落地**：`docker-compose.yml` 中 `redis` 服务命令包含 `--maxmemory 256mb --maxmemory-policy allkeys-lru`（无密码与有密码分支均已配置）。若生产调整内存上限，请同步改 Compose/编排与本段文字。

### 7.3 压缩（可选）

- Nginx 已 **gzip**；若静态资源由构建工具产出且体量大，可在具备模块或 CDN 能力时评估 **Brotli**。

**〔§7.3 实施标注〕** **gzip**：已启用（`nginx/nginx.conf`）。**Brotli**：未实施；若上线，请更新本段与 §11 勾选。
