## 1. 目标与约束

### 1.1 优化目标

- 在**不牺牲安全与数据一致性**的前提下，降低首屏与列表页延迟、提高吞吐、减轻源站与数据库压力。
- 为后续用户量增长预留**可观测、可回滚**的调参空间。

### 1.2 当前环境与硬约束

| 项目 | 说明 |
|------|------|
| 服务器规格 | 腾讯云 **2 核 2G**（见部署清单），CPU 与内存为首要瓶颈 |
| 应用进程 | 生产环境经 **Gunicorn** 启动（见 `entrypoint.sh`） |
| 入口 | **Nginx** 反向代理、HTTPS、静态目录直出 |
| 数据 | **MySQL** 持久化；**Redis** 用于缓存与限流等 |

**原则：** 优先做**可度量、低成本、高收益**项；架构级改造（读写分离、分库）仅在监控证明必要时启动。

## 2. 架构与已有能力（基线）

### 2.1 请求路径

```
用户浏览器 → Nginx (443) → Gunicorn (web:5000) → Flask 应用
                              ↓
                    MySQL / Redis / Celery Worker
```

### 2.2 已具备的能力

- **Nginx**：已对 `/static/` 配置 `expires` 与 `Cache-Control`（见 `nginx/nginx.conf`）；已启用 **gzip**。
- **Gunicorn**：生产命令见 `entrypoint.sh`（含 `workers`、`threads`、`timeout`、访问/错误日志路径）。
- **Redis**：**Flask-Caching** 已接入；**餐厅列表**等场景已实现带版本号的列表缓存与失效逻辑（见 `app/routes/restaurant.py`）。
- **异步**：订单相关任务由 **Celery** 处理（见 `app/tasks/`）。

后续优化应**复用**上述模式（缓存键命名、失效策略、日志位置），避免多套约定并存。

## 4. P0 — 观测与进程配置（必须先做）

### 4.1 日志与指标

| 序号 | 任务 | 说明 |
|------|------|------|
| 1 | **Gunicorn 访问/错误日志** | 确认生产容器内 `logs/access.log`、`logs/error.log` 挂载到宿主机或集中采集，便于按 URL 统计慢请求（部署清单 P1 已列） |
| 2 | **MySQL 慢查询日志** | 开启 `slow_query_log`，`long_query_time` 建议初值 **0.5～1.0** 秒，定期导出 Top SQL |
| 3 | **健康检查** | 已有 `/health`；可配合 crontab 监控与告警（部署清单） |

没有上述数据，后续索引与缓存优化容易变成盲目修改。

### 4.2 Gunicorn 与 2C2G 匹配

当前生产命令（摘录）：

```text
gunicorn --bind 0.0.0.0:5000 --workers 2 --threads 4 --timeout 120 ...
```

**说明：** 在 **2 核 2G** 环境下，`workers=4` 可能导致内存紧张与过多进程竞争。建议：

- 使用 **wrk / Locust** 等对首页、餐厅列表、下单路径做压测；
- 在内存占用与 P99 延迟可接受前提下，尝试 **`workers` 2 + `threads` 2～4** 等组合；
- 以**实测结果**为准更新 `entrypoint.sh`，并在本文档或变更说明中记录压测结论。

### 4.3 数据库连接池

- 核对 **SQLAlchemy** 的 `pool_size`、`max_overflow`、`pool_recycle` 与 MySQL `max_connections`、Gunicorn 进程数的关系，避免出现**连接耗尽**或**闲置连接过多**。
- 修改配置后应做一次压力测试验证。

## 5. P1 — 数据库与应用查询

### 5.1 慢 SQL 与索引

| 序号 | 任务 | 说明 |
|------|------|------|
| 1 | 按慢查询日志排序 | 优先处理**频率高**且**单次耗时高**的语句 |
| 2 | 使用 `EXPLAIN` | 关注 `type`、`key`、`rows`，减少全表扫描 |
| 3 | 复合索引 | 对典型 `WHERE + ORDER BY` 组合建立合适复合索引（需结合具体 SQL） |

### 5.2 ORM：避免 N+1

- 列表页、订单详情等若在循环中访问关联对象，改为 **`joinedload` / `selectinload`** 等预加载，或合并查询。
- 改动后可用日志或 SQL 计数对比请求内 SQL 条数。

### 5.3 地理位置相关（若数据量持续增长）

- 当前有基于 Haversine 的距离筛选与排序；数据量增大时，可考虑**矩形边界预筛选**再精算距离，必要时引入**空间索引**（需评估 MySQL 版本与字段设计）。

---

## 6. P1 — 边缘与静态资源

### 6.1 Nginx 静态缓存

- 已有 `/static/` 的短期缓存；若前端对 CSS/JS 使用**文件名带内容 hash**，可对这类资源配置**更长 `max-age`** 与 `immutable`，减少重复请求。
- **HTML 页面**宜保持较短缓存或依赖协商缓存，避免发版后用户长期看到旧页。

### 6.2 CDN 与对象存储

| 序号 | 任务 | 说明 |
|------|------|------|
| 1 | 图片与大体积静态资源 | 将 `app/static/images/` 等**可公开资源**接入 **腾讯云 COS + CDN**，源站专注动态请求 |
| 2 | 回源与缓存键 | 配置合理缓存规则与 HTTPS；注意**缓存刷新**流程以便更新图片 |

---

## 7. P2 — Redis 缓存扩展与传输优化

### 7.1 只读热点接口缓存

- 对**读多写少**的接口（如餐厅详情、菜单聚合）可参照 `restaurant.py` 中的模式：**短 TTL + 写操作失效**。
- 注意缓存**键命名空间**与**并发下的一致性**（必要时先删缓存再写库，或接受短暂不一致并在文档中说明）。

### 7.2 Redis 自身

- 配置 **`maxmemory`** 与 **`maxmemory-policy`**，避免缓存挤占导致 OOM，影响会话或限流依赖的 Redis 使用。

### 7.3 压缩（可选）

- Nginx 已 **gzip**；若静态资源由构建工具产出且体量大，可在具备模块或 CDN 能力时评估 **Brotli**。
