## 1. 测试计划制定

### 1.1 测试目标

本测试旨在全方位验证在线订餐系统是否达到完整Web应用的预期要求。该系统基于 Flask 框架构建，采用 SQLAlchemy ORM 管理数据库。

本次测试的核心验证目标包括：

1. **功能符合性：** 验证系统所有模块的 CRUD 操作是否符合需求规格，包括用户认证、餐厅管理、菜品管理、购物车、订单管理等。
2. **权限逻辑完备性：** 验证权限体系（user/admin）的访问控制逻辑，确保权限隔离正确。
3. **数据鲁棒性：** 验证系统在面对非法输入、空值、边界条件等情况下的稳定性和错误处理能力。
4. **业务流程完整性：** 验证从用户注册→浏览餐厅→加入购物车→提交订单→订单管理的完整业务闭环。

## 2. 测试用例设计

### 2.1 设计思路

针对Web应用系统的特殊性，本次测试采用"分层覆盖 + 业务驱动"的设计策略，确保既覆盖常规功能路径，又关注高风险场景：

1. **基于等价类划分：**
   - 有效输入类：符合格式要求的正常数据
   - 无效输入类：空值、特殊字符、超长字符串、非法格式
   - 边界值类：价格为0、数量为1、分页边界

2. **基于状态转换：**
   - 订单状态：pending → confirmed → preparing → delivering → completed
   - 订单状态：pending → cancelled
   - 用户角色：user ↔ admin

3. **基于权限控制：**
   - 普通用户访问管理员接口：应返回"权限不足"
   - 未登录用户访问受保护资源：应跳转登录页

4. **基于业务完整性：**
   - 完整购物流程
   - 级联删除验证
   - 数据一致性校验

**缺陷详细分析：**

1. **BUG-001: 权限控制异常 (TC-PERM-02)** [高]
   - **现象：** 普通用户通过直接访问 `/dish/admin` URL，虽触发"权限不足"提示，但页面仍然短暂渲染了管理员数据，存在信息泄露
   - **影响：** 敏感数据泄露，普通用户可查看管理后台内容
   - **修复方案：** 在所有管理员路由的函数入口处添加角色检查：
     ```python
     @dish_bp.route('/admin')
     @login_required
     def admin_dishes():
         if current_user.role != 'admin':
             flash('权限不足')
             return redirect(url_for('dish.list_dishes'))
         # ... 后续管理逻辑
     ```
   - **验证结果：** 在权限控制测试（TC-PERM-01至05）中，所有越权访问尝试均被彻底拦截，无数据泄露。项目中 27 处管理员功能均已实施权限检查
   - **状态：** ✅ 已修复
   - ![image-20251228235939595](C:\Users\Lenovo\Desktop\newdir\images\image-20251228235939595.png)
   
2. **BUG-002 & BUG-003: 图片上传功能异常 (TC-REST-02, TC-DISH-02)** [中]
   - **现象：** 餐厅和菜品编辑时上传图片，系统提示已保存并显示保存路径，但图片未能正常渲染在页面上
   - **根本原因：**
     - 静态文件目录未自动创建，导致文件保存失败
     - 图片保存路径计算逻辑错误，使用了错误的相对路径
     - Flask应用配置中缺少文件上传相关配置
   - **影响：** 无法通过后台管理更新餐厅/菜品图片，影响内容管理功能

**非功能性缺陷详细分析：**

1. **BUG-004: 高并发下用户名唯一性校验竞争** [高]
   
   - **位置：** `app/routes/auth.py` - `register` 函数
   - **问题描述：** 在高并发场景下，两个用户同时使用相同用户名注册。由于代码先查询再插入，存在竞态条件，导致数据库抛出唯一约束冲突异常。
   - **源代码 (有 Bug)：**
     
     ```python
     user = User.query.filter_by(username=username).first()
     if not user:
         new_user = User(username=username, password=hashed_pw)
         db.session.add(new_user)
         db.session.commit()
     ```
   - **修复方案：** 使用数据库原子的唯一约束并配合异常捕获。
     
     ```python
     try:
         new_user = User(username=username, password=hashed_pw)
         db.session.add(new_user)
         db.session.commit()
     except IntegrityError:
         db.session.rollback()
         flash('用户名已存在')
         return redirect(url_for('auth.register'))
     ```
   - **验证结果：** 高并发注册测试通过，唯一约束异常正确捕获并返回友好提示
   - **影响范围：** 注册接口稳定性不足，偶发 500 系统错误（已解决）。
   - **状态：** ✅ 已修复
   
2. **BUG-005: Gunicorn 多工作进程下本地文件日志写入冲突** [高]
   
   - **位置：** `app/utils.py` - `setup_logging`
   - **问题描述：** 当 Gunicorn 开启多个 Worker（如 4 个）时，多个进程同时向 `meituan.log` 写入日志，导致日志条目错位或文件被锁定异常。
   - **修复方案：** 在生产环境下将日志输出从 `RotatingFileHandler` 改为 `StreamHandler(sys.stdout)`，日志由 Docker 日志驱动和 Gunicorn 统一管理，避免多进程文件锁冲突。
     ```python
     # 修复后代码 (app/utils.py)
     def setup_logging(app):
         if not app.debug:
             # 使用 StreamHandler 输出到 stdout
             stream_handler = logging.StreamHandler(sys.stdout)
             stream_handler.setFormatter(logging.Formatter(
                 '%(asctime)s %(levelname)s: %(message)s [in %(pathname)s:%(lineno)d]'
             ))
             stream_handler.setLevel(logging.INFO)
             app.logger.addHandler(stream_handler)
             app.logger.setLevel(logging.INFO)
     ```
   - **验证结果：** 使用 `docker logs` 命令可正常查看应用日志，多进程环境下无日志冲突或丢失。
   - **影响范围：** 生产环境监控失效，错误排查困难（已解决）。
   - **状态：** ✅ 已修复
   
3. **BUG-006: 生产环境 SECRET_KEY 采用默认硬编码安全风险** [高]
   - **位置：** `app/__init__.py`
   - **问题描述：** 应用在生产模式下仍可能回退到代码中硬编码的 `'dev-secret-key'`，这会导致 Session 极易被伪造。
   - **修复方案：** 强制生产环境下必须存在环境变量，否则拒绝启动。
     
     ```python
     if not app.debug and not os.environ.get('SECRET_KEY'):
         raise RuntimeError("Production environment requires SECRET_KEY variable!")
     ```
   - **验证结果：** 生产环境启动测试，缺少 SECRET_KEY 时应用正确拒绝启动并抛出提示信息
   - **影响范围：** 账号接管风险，用户身份可被轻易伪造（已解决）。
   - **状态：** ✅ 已修复
   
4. **BUG-007: 数据库连接池 (Pool Size) 过小导致请求超时** [高]
   - **位置：** `config.py` - `ProductionConfig` 类 / `config_mysql.py` - `ProductionConfig` 类
   - **问题描述：** 在进行 50 并发压力测试时，由于 SQLAlchemy 默认连接池大小仅为 5，导致高并发请求时大量请求报出 `TimeoutError: QueuePool limit of size 5 overflow 10 reached`。
   - **根本原因：** 默认的连接池配置无法满足生产环境高并发场景需求，当超过 15 个并发连接时（pool_size=5 + max_overflow=10），新的数据库请求会被阻塞等待。
   - **修复方案：** 在生产环境配置中优化数据库连接池参数，提升并发承载能力。
     
     **修复后代码** (`config.py` / `config_mysql.py` - `ProductionConfig` 类)：
     ```python
     SQLALCHEMY_ENGINE_OPTIONS = {
         'pool_pre_ping': True,      # 连接前检测连接是否有效
         'pool_size': 20,             # 连接池大小（从默认5提升至20）
         'max_overflow': 10,          # 最大溢出连接数（超过pool_size后的额外连接）
         'pool_recycle': 3600,        # 连接回收时间（秒），防止MySQL连接超时
         'echo': False                # 不显示SQL语句
     }
     ```
   - **优化效果：** 
     - 最大可支持 30 个并发数据库连接（pool_size 20 + max_overflow 10）
     - 连接回收时间延长至 1 小时，减少连接重建开销
     - 增加连接健康检查，提高连接可用性
   - **验证结果：** 
     - ✅ 50 并发测试：平均响应时间0.287s，成功率99.5%
     - ✅ 100 并发测试：平均响应时间0.342s，成功率99.2%
     - ✅ 500 并发测试：平均响应时间0.618s，成功率98.1%
     - ⚠️ 1000 并发测试：平均响应时间1.247s，成功率95.8%，建议进一步优化
   - **影响范围：** 业务高峰期网站频繁假死或报 500 错误（已解决）。
   - **状态：** ✅ 已修复
