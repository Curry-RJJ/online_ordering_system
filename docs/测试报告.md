## 1. 测试计划制定

### 1.1 测试目标

本测试旨在全方位验证在线订餐系统是否达到完整Web应用的预期要求。该系统基于 Flask 框架构建，采用 SQLAlchemy ORM 管理数据库。

本次测试的核心验证目标包括：

1. **功能符合性：** 验证系统所有模块的 CRUD 操作是否符合需求规格，包括用户认证、餐厅管理、菜品管理、购物车、订单管理等。
2. **权限逻辑完备性：** 验证权限体系（user/admin）的访问控制逻辑，确保权限隔离正确。
3. **数据鲁棒性：** 验证系统在面对非法输入、空值、边界条件等情况下的稳定性和错误处理能力。
4. **业务流程完整性：** 验证从用户注册→浏览餐厅→加入购物车→提交订单→订单管理的完整业务闭环。

### 1.2 测试范围与规格分析

根据代码分析，本次测试覆盖以下核心模块。测试团队已建立详细的需求追踪表格以确保测试覆盖率。

## 2. 测试用例设计

### 2.1 设计思路

针对Web应用系统的特殊性，本次测试采用"分层覆盖 + 业务驱动"的设计策略，确保既覆盖常规功能路径，又关注高风险场景：

1. **基于等价类划分：**
   - 有效输入类：符合格式要求的正常数据
   - 无效输入类：空值、特殊字符、超长字符串、非法格式
   - 边界值类：价格为0、数量为1、分页边界

2. **基于状态转换：**
   - 订单状态：pending → confirmed → preparing → delivering → completed
   - 订单状态：pending → cancelled
   - 用户角色：user ↔ admin

3. **基于权限控制：**
   - 普通用户访问管理员接口：应返回"权限不足"
   - 未登录用户访问受保护资源：应跳转登录页

4. **基于业务完整性：**
   - 完整购物流程
   - 级联删除验证
   - 数据一致性校验

##### **BUG-007: Docker 容器时区未同步导致订单时间偏差 🔴**

*   **严重程度**: 严重 (P1)
*   **位置**: `Dockerfile` / 基础环境配置
*   **问题描述**: 
    容器默认运行在 UTC 时区，导致所有产生的订单记录在数据库中的 `created_at` 时间比北京时间晚 8 小时。

    FROM python:3.7-slim

    RUN ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ > /etc/timezone
    ```

*   **影响范围**: 订单配送时间计算错误，影响财务对账与配送逻辑。
*   **状态**: ✅ 已修复

##### **BUG-008: Docker 挂载目录权限冲突导致图片上传失败 🔴**

*   **严重程度**: 严重 (P1)
*   **位置**: `app/utils.py` - `save_uploaded_image`

    # entrypoint.sh

    exec "$@"
    ```

##### **BUG-015: 高并发下手机号唯一性校验竞争 🔴**

*   **严重程度**: 严重 (P1)
*   **位置**: `app/routes/auth.py` - `register` 函数
*   **问题描述**: 
    在高并发场景下，两个用户同时使用相同手机号注册。由于代码先查询再插入，存在竞态条件，导致数据库抛出唯一约束冲突异常。

*   **源代码 (有 Bug)**:
    ```python
    user = User.query.filter_by(phone=phone).first()
    if not user:
        new_user = User(phone=phone, ...)
        db.session.add(new_user)
        db.session.commit()
    ```

*   **修复方案**:
    使用数据库原子的唯一约束并配合异常捕获。
    ```python
    try:
        new_user = User(phone=phone, ...)
        db.session.add(new_user)
        db.session.commit()
    except IntegrityError:
        db.session.rollback()
        return "手机号已被占用", 400
    ```

*   **影响范围**: 注册接口稳定性不足，偶发 500 系统错误。
*   **状态**: ✅ 已修复

##### **BUG-017: 餐厅列表加载时的数据库 N+1 查询瓶颈 🔴**

*   **严重程度**: 严重 (P1)
*   **位置**: `app/routes/restaurant.py` - `list_restaurants`
*   **问题描述**: 
    在首页加载餐厅列表时，每展示一个餐厅都会触发一次额外的数据库查询来获取其关联的菜品统计信息，导致在商家数量较多时，页面响应时间呈线性增长（即经典的 N+1 问题）。

*   **源代码 (有 Bug)**:
    ```python
    # 循环中触发懒加载查询
    restaurants = Restaurant.query.all()
    for r in restaurants:
        count = r.dishes.count() # 每次循环都产生一次 SQL 查询
    ```

*   **修复方案**:
    使用 SQLAlchemy 的 `joinedload` 或 `subqueryload` 进行预加载（Eager Loading），将 N 次查询优化为 1 次复合查询。
    ```python
    from sqlalchemy.orm import joinedload
    restaurants = Restaurant.query.options(joinedload(Restaurant.dishes)).all()
    ```

*   **影响范围**: 随着入驻商家增加，首页打开速度将显著变慢，极大影响用户首屏体验。
*   **状态**: ✅ 已修复
